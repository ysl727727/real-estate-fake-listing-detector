# 프로젝트 노트 — 허위매물 탐지 어시스턴트

## STEP 1. 문제 정의

**허위매물 탐지 어시스턴트**

매물 광고 정보를 국토교통부고시 「부당한 중개대상물 표시·광고행위의 유형 및 기준」
(제2026-345호, 2026.7.3. 일부개정)에 대조해 부당 표시·광고 해당 여부와 유형을
판정하는 어시스턴트에 사용할 로컬 모델을 선정한다.

- 사용자: 부동산 플랫폼 매물 검수 담당자
- 답해야 할 질문: 광고가 고시 기준에 해당하는지, 어느 유형인지, 근거는 무엇인지
- 한국어 성능: 중요 (기준·광고·판정이 모두 한국어)
- 데이터 통제: 미검수 매물 정보와 중개사 정보가 포함되므로 로컬 운영에 근거가 있음
- 응답 속도: 중요도 중간 (실시간 대화가 아닌 검수 배치 작업)
- GPU 환경: RTX 5060 Laptop 8GB

**자료 제공 방식**: 고시 조항을 프롬프트에 직접 포함. 검색·RAG 없음(in-context QA).

### 이 Use Case를 고른 이유
- 공식 판정 기준이 존재해 정답이 객관적으로 정해진다 ("방향 90도 이상 차이" 등 수치 기준)
- 판정/유형/근거 3줄로 출력 형식을 강제할 수 있어 Instruction Following을 점수화할 수 있다
- 미검수 매물·중개사 정보를 다루므로 로컬 운영의 근거가 자연스럽다
- 수치 기준이 있어 상식과 기준이 어긋나는 경계 사례를 설계할 수 있다

### 선택 이유

- License 성격이 대조적이어서 도입 조건 검토 관점에서 비교 가치가 있음
- 8GB VRAM에서 여유 있게 실행 가능 (4B급이 현실적 상한선 안쪽)

### 검토 후 제외한 후보
**qwen3:8b** — 파라미터를 키운 비교를 검토했다.
2507 시리즈는 4B, 30B-A3B, 235B-A22B에만 제공되며 **8B용 instruct 전용 태그가 없다.**
qwen3:8b는 thinking 모드가 포함된 기본 태그뿐이다.

기본 후보인 4b-instruct-2507은 비추론 영역을 독립시켜 추가 학습한 모델이므로,
8B에서 추론을 끄더라도 튜닝 방식이 다르다. 파라미터 크기만 분리한 비교가
성립하지 않아 제외했다.

같은 계열의 다음 크기인 30B-A3B-Instruct-2507은 MoE 구조이고 8GB VRAM을
초과하므로 이번 장비에서는 실행할 수 없다.

### 양자화에 대한 기록 (기본 과제 범위)
두 후보 모두 Q4_K_M 양자화 버전을 사용했다. 양자화는 모델 가중치를 낮은 비트로
표현해 VRAM 사용량과 파일 크기를 줄이고, 8GB VRAM 노트북에서 4B 모델을 GPU에
온전히 올릴 수 있게 하는 기법이다. 대신 원본(FP16) 대비 품질 손실 가능성이 있다.

`q4_K_M`의 의미: q4는 4비트 양자화, K는 블록 단위로 스케일을 따로 저장해 정보
손실을 줄이는 K-quant 방식, M은 Medium으로 파일 크기와 품질의 중간 지점이다.

두 후보의 양자화 수준이 동일하므로 관찰된 차이는 양자화 효과가 아니라 모델 자체의
차이로 본다. 양자화 버전 간 직접 비교는 선택 실습 A에서 수행했다.

한 가지 답만 반복해서는 최대 4/10이 상한이다.

### 자료 설계 원칙
- **조항은 필요한 것만 발췌**한다. 전문을 넣으면 긴 입력 처리 능력이 섞여 모델 비교가
  오염되고, 사실상 검색 과제가 되어 이번 범위를 벗어난다. 실제 입력은 376~638 토큰을 유지했다.
- **유형명을 반드시 포함**한다. 시범 실행에서 조항만 있고 유형명이 없어 두 모델 모두
  유형을 틀린 적이 있다. 답할 수 없는 문항이었으므로 10문항 전체를 보완했다.
- **오답 선택지를 함께 넣는다.** 정답 조항 하나만 주면 베끼면 되므로, 관련 없는 조항 중에서
  골라내는 능력을 보도록 구성했다.

**Q06·Q07 설계 의도**: 겉보기와 요건 적용 결과가 어긋나도록 만들었다.
Q06은 45도 차이로 상식적으로는 위반 같지만 기준은 90도 이상이다.
Q07은 계약 완료 매물이 게시 중이지만 "기망 행위가 확인된 경우"라는 요건을 충족하지 않는다.
모델이 자료의 조건절을 판정에 반영하는지를 보는 문항이다.

### 통제 조건
- system 프롬프트: 10개 질문 전체, 두 모델 모두 동일
- 출력 형식 강제: `판정:` / `유형:` / `근거:` 3줄
- 질문마다 messages를 새로 생성. 이전 질문의 대화 이력을 이어 붙이지 않음
- 답변에 판정이 여러 번 등장하면 **첫 번째 '판정:' 줄을 공식 출력**으로 본다.
  자동화 파이프라인이 그 줄을 파싱하기 때문이다.

### 채점 방식
- `questions.json`의 `expected` 체크리스트 항목당 1점
- 질문마다 만점이 다르므로 **획득/만점 = 달성률(%)** 로 환산해 비교
- 점수와 함께 근거가 된 응답 문장을 인용해 기록
- 호출 성공 여부와 답변 품질 통과 여부는 구분해 기록
- `verdict` 열에 모델이 실제로 출력한 판정값을 기록

**5점 척도 대신 체크리스트를 쓴 이유**: "정확성 4점"은 왜 4점인지 설명이 안 된다.
체크리스트는 판정 근거가 답변 안에 있어 다른 사람이 재채점해도 비슷한 결과가 나온다.
그리고 항목을 나눠두면 실패 원인이 드러난다. gemma3가 "판정은 맞는데 조항 인용이
빗나간다"는 패턴을 잡아낼 수 있었던 것이 그 때문이다.

**단순 합산 대신 %로 환산한 이유**: 문항마다 만점이 달라 그냥 더하면 항목이 많은
문항이 더 무거워진다. 문항별 달성률의 평균을 써서 10개 문항을 동일 가중으로 처리했다.

### 채점 항목 수정 (채점 중 발견)
Q09·Q10의 `expected`에 있던 '확인처를 안내했는가' 항목을 채점에서 제외했다.
system 프롬프트가 요구하지 않은 행동이므로, 이를 근거로 감점하면 평가 조건이
불공정해지기 때문이다. 수정 후 만점은 Q09 2점, Q10 3점이며 두 모델에 동일 적용했다.

### Cloud 비교용 질문 5개 (결과를 보기 전에 선정)
**Q01, Q03, Q05, Q06, Q10**
- 정상 3 / 경계 1 / 범위밖 1로 원래 비율(5:3:2)을 유지
- 반복 수: 로컬 각 2회, Cloud 각 1회 — 비교표에 반드시 표시

- 결과: 40/40 성공. gemma3 50.1% / qwen3 75.6%
- **제외 사유**: Cloud와 temperature는 맞췄으나 seed를 지정하지 않아
  로컬 두 모델 간 재현성이 확보되지 않았다. 튜터 피드백을 반영해 seed를 고정하고 재실행했다.
- 양자화 비교(선택 실습 A)도 이 조건으로 한 차례 수행했으며 함께 보관했다.

### 3차 실험 (본 집계 대상)
- 생성 설정: temperature **1**, num_predict 1024, num_ctx 4096, **seed 42**
- 로컬: `results/runs.jsonl` — 40/40 성공, 실패 없음
- Cloud: `results/cloud.jsonl` — 5/5 성공, 추정 비용 $0.001097
- 양자화: `results/runs_quant.jsonl` — 40/40 성공
- 품질: gemma3 57.0% / qwen3 80.8% / cloud-luna 100%(공통 5문항)

### seed를 고정한 이유
2차 실험에서는 Cloud와 실행 환경이 달라 seed가 재현을 보장하지 못한다는 이유로
양쪽 모두 미지정으로 두었다. 그러나 이는 **로컬과 Cloud 사이에만 해당하는 얘기**였다.

로컬 두 모델은 같은 기계·같은 Ollama에서 실행되므로 seed 고정이 재현성을 높인다.
Cloud 쪽은 효과가 없지만 손해도 없다. 한쪽은 이득이고 한쪽은 무해하므로
양쪽 모두 42로 고정하는 것이 맞다고 판단했다.

Cloud 모델이 seed 파라미터를 수용하는지는 사전 테스트로 확인했다.
(`max_tokens`와 `temperature=0`은 거부당했으나 `seed`는 수용됨)

## 관찰 사항

### seed 고정의 효과와 한계

**효과가 확인됐다.** 선택 실습 A에서 같은 조건의 q4_K_M을 다시 측정했을 때
기본 실험과 **글자 단위로 동일한 답변**이 나왔고 점수도 80.8%로 일치했다.
2차 실험(seed 미지정)에서는 같은 q4_K_M이 75.6%와 82.5%로 갈렸다.
회차 편차 6.9%p가 양자화 간 차이보다 커서 당시에는 해석이 불가능했다.

**다만 완전한 재현은 보장되지 않는다.** temperature 1에서는 seed 42를 고정해도
회차 간 출력 토큰 수가 달라지는 문항이 있었다(Q02 qwen3 234 vs 160,
Q06 qwen3 928 vs 453 등). 1차 실험(temperature 0 + seed 42)에서는
19개 문항이 토큰 단위로 동일했던 것과 대비된다.

temperature 0에서는 확률 최상위만 선택하므로 난수를 사용하지 않기 때문으로 보인다.
즉 **seed 고정이 재현성을 보장하는 것은 temperature가 0에 가까울 때**이며,
temperature 1에서는 seed만으로 재현이 확보되지 않는다. 정확한 원인은 추가 확인이 필요하다.

### 세 차례 실험에서 결론이 일치함
| 조건 | gemma3 | qwen3 | 격차 |
|---|---|---|---|
| temperature 0 / seed 42 | 55.1% | 85.0% | 29.9%p |
| temperature 1 / seed 미지정 | 50.1% | 75.6% | 25.5%p |
| temperature 1 / seed 42 | 57.0% | 80.8% | 23.8%p |

생성 설정을 세 가지로 바꿔도 선정 결과가 동일하다.
qwen3는 세 조건 모두에서 정상 문항 5개를 100% 달성했다.

### gemma3의 실패 양상은 조건마다 달라진다
같은 문항에서 항상 틀리지만, **틀리는 방식이 바뀐다.**

| 문항 | 1차 (temp 0) | 3차 (temp 1 + seed) |
|---|---|---|
| Q05 | 판정 칸에 유형 선택지 '해당없음' 기입 (형식 붕괴) | 판정 칸에 '판단불가' 기입 (형식은 준수, 판정 오답) |
| Q07 | "요건이 없으므로 해당합니다" 자기모순 | "권유한 사실이 확인되었습니다"로 자료를 반대로 읽음 |

"정상 광고를 정상으로 판정하지 못한다", "자료를 판정에 반영하지 못한다"는
결론은 일관되나, 구체적 증상은 조건에 따라 다르게 나타난다.

### gemma3의 조항 인용 불안정
Q02·Q03에서 "광고 시 제시한 옵션의 성능을 실제와 다르게 표시한 경우"라는 동일한
문장이 반복된다. 방향(Q02)과 직선거리(Q03)는 각각 다른 조항인데 같은 문구를 쓴다.
Q04는 세 차례 실험 모두 1회차가 (가) 가격 조항, 2회차가 (다) 사진 조항으로 갈렸다.

### qwen3의 Q06 실패는 설정과 무관하다
| 실험 | 출력 토큰 | 결과 |
|---|---|---|
| temp 0 + seed 42 (np 512) | 512 (절단) | 첫 판정 줄 '해당' |
| temp 0 + seed 42 (np 1024) | 1024 (절단) | 첫 판정 줄 '해당' |
| temp 1 + seed 미지정 | 655 / 290 | 첫 판정 줄 '해당' |
| temp 1 + seed 42 | 928 / 453 | 첫 판정 줄 '해당' |

**45<90 계산은 네 조건 모두 정확했다.** 그런데 첫 판정 줄을 고치지 못한다.
답을 다 쓰고 나서 "재검토", "정정"이라며 아래에 다시 쓰는 식이다.
생성은 되돌릴 수 없으므로 처음에 판정을 확정해야 하는데 그것을 못 한다.

Cloud는 같은 문항을 71토큰, 두 문장으로 끝냈다. 계산 능력이 아니라
**결론을 내고 멈추는 능력**의 차이로 보인다.

### 판단 유보 판단의 실패 (다섯 조건 모두)
Q08은 '현저하게'의 수치 기준이 자료에 없어 정답이 '판단불가'다.
세 차례 기본 실험과 양자화 q4/q8 모두 두 모델이 단정적으로 판정했다.
**아무도 '판단불가'를 선택하지 못했다.**

반대로 기준이 명확한 Q06에서는 '판단불가'로 가려는 경향이 나타났다.
유보가 필요한 상황과 아닌 상황을 반대로 처리하는 셈이다.
Cloud만 Q06을 '미해당'으로, Q10을 '판단불가'로 정확히 구분했다.

### 양자화로 해결되지 않는 한계
선택 실습 A에서 q4_K_M과 q8_0이 **같은 문항(Q06, Q08)에서 똑같이 실패**했다.

- Q06: 45도 < 90도 계산은 두 버전 모두 정확했으나, 첫 판정 줄에 '해당'을 쓰고
  뒤에서 정정하는 패턴이 동일했다. 정밀도가 아니라 **결론을 확정하고 멈추는 능력**의 문제다.
- Q08: '현저하게'의 수치 기준이 없는데 두 버전 모두 단정했다.
  **판단 유보가 필요한 상황을 인식하지 못하는 문제**다.

반면 정밀도를 높였을 때 개선된 영역도 있었다. Q03에서 자료의 `400m`를 q8은 정확히
생성했으나 q4는 '40지점'으로 잘못 생성했고, Q06에서 q4만 '4가 아닌 45도' 토큰 깨짐이
발생했다. 숫자 토큰 생성은 정밀도에 민감한 것으로 보인다.

정리하면 **양자화 수준은 표기 정확도에 영향을 주지만 판단 능력에는 영향을 주지 않았다.**

### tokens/s가 실행 중 변동함
gemma3의 tokens/s가 Q01~Q06 구간 68~79, Q07 이후 약 100으로 뛴다.
세 차례 실험 모두 **같은 지점에서 재현**됐다. GPU 전력 상태나 장비 워밍업의
영향으로 보이며, 모델의 성능 차이로 해석해서는 안 된다.
qwen3는 전 구간 약 100으로 일정했다.

→ 평균만 표시하면 이 변동이 묻히므로, 최소/최대와 함께 기록한다.

### 입력 토큰 수가 모델별로 다름
같은 질문인데 qwen3의 `prompt_eval_count`가 gemma3보다 60~90 토큰 많다.
토크나이저가 달라서 생기는 차이이며, tokens/s만으로 체감 속도를 비교하면 안 되는
이유다. 전체 응답 시간을 함께 본다.

### VRAM
- gemma3: 2742.3 MiB (전 회차 일관)
- qwen3: 3030.9 MiB (전 회차 일관)
- `client.ps()`의 `size_vram`을 각 응답 직후 조회한 값이며, 최대 VRAM 사용량이 아니다.

### 모델 로딩 시간
본 실험 20회의 `load_duration`은 모두 0.001~0.002초다. 모델이 이미 메모리에
올라온 상태에서 호출했기 때문이며 실제 로딩 시간이 아니다.
로딩 시간 비교는 워밍업 1회 값을 사용한다 (gemma3 4.117초 / qwen3 2.045초).

## Local–Cloud 비교

### 조건 일치 여부 (3차 실험 기준)
**맞춘 것**: system 프롬프트, 자료, messages 구조, temperature 1, seed 42, 출력 한도 1024

**맞출 수 없는 것**
- 반복 수 (로컬 2회 / Cloud 1회) — 발제 지정
- 질문 수 (로컬 10개 / Cloud 5개) — 발제 지정
- context 길이: 로컬은 num_ctx 4096 명시, Cloud는 지정 불가(모델 기본값)
- 출력 한도 파라미터명이 다름 (`num_predict` / `max_completion_tokens`)
- 실행 환경: 로컬 GPU vs 원격 서버 + 네트워크. seed를 양쪽에 넣었으나 재현이 연결되지는 않음
- 모델 규모: 4B vs 미공개

1·2차 실험에 있던 생성 설정 불일치는 모두 해소됐다.

### Cloud 호출 방식
2번 가이드 예제(`02_luna_chat.py`)는 Responses API를 사용하지만,
`run_cloud.py`는 로컬(Ollama)과 동일한 messages 구조를 유지하기 위해
Chat Completions API를 사용했다. system/user 역할 분리와 프롬프트 구성을
로컬과 같게 맞추기 위함이다.

### Cloud 모델의 내부 추론 사용 여부 확인
`gpt-5.6-luna`는 none / low / medium / high / xhigh / max의 추론 수준을 제공하는
모델이다. 로컬 후보가 non-thinking 전용이므로 조건이 어긋날 가능성을 확인했다.

`usage.completion_tokens_details.reasoning_tokens`를 직접 측정한 결과
단순 인사말과 실제 실험 문항(Q06) 모두 **0**이었다.
이번 실험에서 사용한 Chat Completions 엔드포인트에서는 추론이 동작하지 않은 것으로
보이며, 로컬과 Cloud 양쪽 모두 내부 추론 없이 실행된 것으로 확인된다.
확인 스크립트는 `check_reasoning.py`로 저장소에 남겼다.

**주의**: "이 모델은 추론을 쓰지 않는다"가 아니라 "이번 구성에서는 쓰이지 않았다"가
정확한 서술이다. 추론 수준을 올렸을 때의 품질·비용·응답 시간 변화는 측정하지 않았다.
Cloud가 공통 5문항에서 100%를 기록한 것은 추론 없이 얻은 결과다.

참고로 이 계열은 Chat Completions에서 tools와 추론을 동시에 쓸 수 없다는 제한이
있으며, 추론을 제어하려면 Responses API를 쓰는 것이 일반적이다. 다만 Responses는
입력 구조가 `instructions` / `input`으로 나뉘어 로컬 Ollama의 `messages` 구조와
달라지므로, 프롬프트 전달 방식을 동일하게 유지하기 위해 Chat Completions를 유지했다.

### Cloud에 워밍업을 두지 않은 이유
워밍업은 모델을 디스크에서 VRAM으로 올리는 시간을 본 실험에서 분리하기 위한 것이다.
Cloud는 제공자 서버에 모델이 이미 떠 있으므로 해당 개념이 없다.

다만 첫 호출이 3.89초로 가장 느리고 이후 1.82~3.59초로 낮아졌다.
네트워크 연결 수립의 영향으로 보이며, 로컬의 모델 로딩과는 성격이 다르다.

### Cloud API 호출 시 발생한 실패 (운영 난이도 근거)
1. 프로젝트 키에 `gpt-4o-mini` 접근 권한 없음 (403)
2. `max_tokens` 미지원 → `max_completion_tokens` 사용 필요 (400)
3. `temperature=0` 미지원, 기본값 1만 허용 (400)

로컬 Ollama는 설치 후 첫 시도에 동작했다. Cloud는 제공자가 정한 파라미터 규격에
맞춰야 하며, 규격이 바뀌면 코드를 고쳐야 한다.

- 질문 10개 × 2회 × 2버전 = 40회, 호출 성공 40/40
- 두 버전 모두 `ollama ps`에서 100% GPU 적재 확인
- **양자화 수준만 다르고 나머지 조건은 전부 동일하다.** 서로 다른 모델의 차이를
  양자화 효과로 해석하지 않기 위해 같은 모델의 두 버전만 사용했다.

### 결과
| 지표 | q4_K_M | q8_0 |
|---|---|---|
| VRAM | 3030.9 MiB | 4731.4 MiB (+1700.5, 1.56배) |
| 생성 속도 | 88.82 tok/s | 69.57 tok/s (−22%) |
| 품질 | **80.8%** | 75.9% (−4.9%p) |
| 전체 응답 시간 | 2.50초 | 2.81초 |
| 출력 토큰 수 | 216.4 (120~928) | 191.15 (99~754) |
| 로딩 시간 (워밍업) | 2.033초 | 4.719초 |

### 측정의 신뢰성
q4_K_M이 기본 실험과 동일한 80.8%로 재현됐다. seed 42 덕분에 답변이 글자 단위로
같았다. 2차 실험(seed 미지정)에서는 같은 q4_K_M이 75.6%와 82.5%로 갈려
회차 편차가 양자화 간 차이보다 컸고, 당시에는 "의미 있는 차이가 관측되지 않았다"고만
쓸 수 있었다. seed 고정으로 변수를 제거한 뒤에야 해석이 가능해졌다.

### 속도 비교 시 주의
q4의 측정값이 68.59~102.25로 폭이 넓다. Q01~Q04 구간이 68~79이고 Q05 이후 92~102인데,
먼저 실행되어 장비 워밍업 구간이 섞인 결과다. q8은 68.70~70.52로 일정하다.
안정 구간끼리 비교하면 q4 약 101 vs q8 약 69로 q4가 약 45% 빠르다.

### q8의 감점 원인
4.9%p 차이의 대부분이 **유형 칸 오기입**에서 나왔다.
- Q04(사진 도용): 근거는 (다) 정확, 유형은 '부존재·허위' (두 회차)
- Q07(미해당): 판정·근거 정확, 유형은 '부존재·허위' (두 회차)

정답은 각각 '거짓·과장'과 '해당없음'이다. q4는 이 오류가 없었다.

### q8이 앞선 항목
- **Q03 숫자 생성**: 자료의 `400m`를 q8은 두 회차 모두 정확히 생성. q4는 두 회차 모두
  '40지점'으로 잘못 생성. 2차 실험에서도 같은 패턴이었다.
- **Q06 토큰 깨짐**: q4 1회차에서 "4가 아닌 45도" 발생. q8에는 없었다.
- **Q10 범위 밖 안내**: q8만 손해배상·승소 가능성이 판정 기준 밖임을 명시.
- **간결성**: Q02에서 q4는 (라)·(가)를 검토·기각하는 과정이 노출돼 234토큰,
  q8은 124토큰으로 (다)에 바로 도달. Q07에서도 q4 186토큰 vs q8 104토큰.

### 결론
이 Use Case에서는 q4_K_M이 합리적이다. VRAM을 1.7 GB 덜 쓰고 생성이 빠르며
품질도 앞섰다.

다만 정밀도를 높였을 때 개선되는 영역도 확인됐다(숫자 생성, 범위 밖 안내, 간결성).
숫자 정확도가 중요한 태스크라면 다시 검토할 여지가 있다.

두 버전 모두 같은 문항(Q06, Q08)에서 실패했으므로 정밀도로 해결되지 않는
한계가 있다는 점도 확인됐다.

## 선택 실습 B — 임베딩 실험 (수행 완료)

- 모델: `paraphrase-multilingual-MiniLM-L12-v2` (384차원)
- 스크립트: `embedding_test.py`
- 흐름: 문장 → 임베딩 벡터 → 코사인 유사도 → 의미 유사도 확인
- 참고: 실행 중 PyTorch의 `torch_python.dll`이 애플리케이션 제어 정책에 의해
  차단되어(OSError: WinError 4551) 한 차례 실패했으나 재부팅으로 해소됐다.

### 1부 발제 예시
기준 "고양이가 소파 위에 있다."
- "소파 위에 고양이가 앉아 있다." → **0.9509**
- "오늘 주식시장이 상승했다." → **−0.011**

어순이 바뀌고 표현이 달라도 의미가 같으면 벡터 공간에서 가깝고,
무관한 문장은 음수까지 떨어진다.

### 2부 방향 사례 → 판정 기준 매칭 (정답 (다))
| 조항 | 유사도 |
|---|---|
| (다) 방향 90도 이상 차이 | **0.6791** |
| (라) 직선거리 표시 | 0.6329 |
| (가) 옵션 성능 | 0.5896 |
| (나) 관리비 차이 | 0.4269 |

정답 조항이 1위였으나 2위와 차이가 0.046에 불과하다.

### 3부 직선거리 사례 → 판정 기준 매칭 (정답 (라))
| 조항 | 유사도 |
|---|---|
| (다) 방향 90도 이상 차이 | 0.3573 |
| (라) 직선거리 표시 | 0.3298 |
| (나) 관리비 차이 | 0.2787 |
| (가) 옵션 성능 | 0.2143 |

**정답 조항이 2위로 밀렸다.** 전체 점수대도 0.21~0.36으로 2부의 절반 수준이다.
사례는 "지하철역·도보 5분·13분", 조항은 "주요 교통시설·도보거리·직선거리"로
의미는 같으나 어휘가 겹치지 않는다. 반면 (다)는 "광고했으나 실제로는"이라는
문장 구조가 사례와 닮아 더 높게 나왔다.

### 관찰
단순 임베딩 유사도만으로는 법 조항 매칭이 신뢰할 수준이 아니다.
2건 중 1건에서 오답 조항이 1위였다.

이번 프로젝트가 자료를 프롬프트에 직접 제공하는 방식(in-context QA)을 택한 것이
결과적으로 이 위험을 피한 셈이다. 향후 RAG를 도입한다면 모델 성능과 별개로
검색 단계의 정확도를 따로 평가해야 하며, 유사도 값을 판정의 사실성 점수로
해석해서는 안 된다.

이 실습은 생성 모델의 내부 토큰 표현이 아니라 문장 비교용 임베딩을 사용했고,
같은 임베딩 모델·같은 설정으로 얻은 벡터끼리만 비교했다.
Vector DB나 RAG 시스템은 구현하지 않았다.
